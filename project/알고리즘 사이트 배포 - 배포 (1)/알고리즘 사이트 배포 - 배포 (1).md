# 알고리즘 사이트 배포 - 배포 (1)

알고리즘 사이트 개발은 어느 정도 완성되었다. 이제 드디어 배포 단계다. 배포 과정을 작성해 보겠다.

## 1. EC2 생성

클라우드 서비스는 AWS를 선택했다. 다른 서비스보다 비용이 비싸지만, 많이 사용되는 서비스를 직접 경험해 보기 위해서다.

AWS 신규 고객은 가입 시 100달러의 크레딧을 받고, 서비스 이용에 따라 최대 100달러를 추가로 받을 수 있다. 기존 계정은 이미 프리 티어를 사용했기 때문에 새 계정에서 EC2 인스턴스를 생성했다.

내 PC에서 SSH를 통해 EC2에 접속하고, 외부에서는 HTTP와 HTTPS로 접근할 수 있어야 한다. 따라서 인바운드 규칙은 아래와 같이 설정한다.

- 22(SSH): 내 IP
- 80, 443(HTTP/HTTPS): Anywhere

다만 네트워크 환경이 바뀔 때마다 22번 포트의 인바운드 규칙을 수정해야 한다. 번거롭지만 SSH 접근 범위를 제한하기 위해 필요하다.

생성 과정은 생략하겠다.

### 어떤 인스턴스 유형을 골라야 할까?

알고리즘 플랫폼에는 프론트엔드 서버, 백엔드 서버, 채점 서버, DB가 필요하다. 우선 한 인스턴스에서 모두 실행하려고 하는데, 채점 서버가 비교적 많은 리소스를 사용한다.

운영할 때는 적어도 8GB RAM을 제공하는 `t3.large`를 사용하려고 한다. 하지만 `t3.large`는 한 달에 약 75달러가 필요하다. 현재는 트래픽이 거의 없는 단계이므로 2GB RAM을 제공하는 `t3.small`을 사용한다. 비용은 한 달에 약 19달러다.

## 2. Private Repository Clone

비공개 저장소를 `clone`하려고 했지만 GitHub 아이디와 비밀번호로는 인증되지 않았다.
GitHub 계정 비밀번호 대신 토큰을 사용해야 하므로 Fine-grained personal access token을 발급받았다.

`git clone` 명령어를 실행한 뒤 GitHub 아이디와 발급받은 토큰을 입력하면 된다.

## 3. 필요한 패키지 설치

인스턴스 운영체제는 `Amazon Linux 2023`이다. 패키지 관리자인 `dnf`를 사용해 필요한 패키지를 설치한다.

기본 도구 설치

```bash
sudo dnf install -y curl git tar gzip xz nginx docker rsync java-21-amazon-corretto-devel
```

Docker, Nginx 실행

```bash
sudo systemctl enable --now docker
sudo systemctl enable --now nginx
sudo usermod -aG docker "$USER"
```

그룹 변경 사항을 적용하려면 다시 로그인한다.

Node.js, npm 설치

`nvm` 설치

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
```

`nvm`으로 Node.js 설치

```bash
export NVM_DIR="$HOME/.nvm"
source "$NVM_DIR/nvm.sh"

nvm install 22
nvm use 22
nvm alias default 22

npm --version
```

Go 설치

`uname -m`의 결과가 `x86_64`라면 아래 명령어를 실행하면 된다.

```bash
GO_ARCH=amd64

cd /tmp
curl -LO "https://go.dev/dl/go1.26.4.linux-${GO_ARCH}.tar.gz"

sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf "go1.26.4.linux-${GO_ARCH}.tar.gz"
```

PATH 등록

```bash
echo 'export PATH=$PATH:/usr/local/go/bin' >> "$HOME/.bashrc"
export PATH="$PATH:/usr/local/go/bin"
```

## 5. 백엔드 빌드

빌드

```bash
./gradlew clean bootJar
```

### 환경 변수 파일 생성

```bash
sudo mkdir -p /etc/ps-platform
sudo nano /etc/ps-platform/backend.env
```

아래 내용을 저장한다.

```dotenv
SPRING_PROFILES_ACTIVE=prod
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=ps_platform
DB_USERNAME=<username>
DB_PASSWORD=<password>

JWT_SECRET=<my-key> # openssl rand -base64 48로 생성 가능
JWT_ACCESS_TOKEN_TTL_SECONDS=900
JWT_REFRESH_TOKEN_TTL_SECONDS=1209600
```

권한 설정

```bash
sudo chmod 600 /etc/ps-platform/backend.env
```

### 서비스 파일 생성

```bash
sudo nano /etc/systemd/system/ps-platform-backend.service
```

```ini
[Unit]
Description=PS Platform Backend
After=network-online.target docker.service
Wants=network-online.target
Requires=docker.service

[Service]
Type=simple
User=ec2-user
WorkingDirectory=/home/ec2-user/ps-platform/backend
EnvironmentFile=/etc/ps-platform/backend.env
ExecStart=/usr/bin/java -jar /home/ec2-user/ps-platform/backend/build/libs/backend-0.0.1-SNAPSHOT.jar
Restart=on-failure
RestartSec=5
SuccessExitStatus=143

[Install]
WantedBy=multi-user.target
```

`systemd`에 데몬 등록

> 데몬: 터미널에 연결되지 않은 상태로 백그라운드에서 계속 실행되는 프로그램

```bash
sudo systemctl daemon-reload
sudo systemctl enable ps-platform-backend
sudo systemctl list-unit-files | grep ps-platform
```

### 서비스 파일 생성

```bash
sudo nano /etc/systemd/system/ps-platform-judge-worker.service
```

```ini
[Unit]

After=network-online.target docker.service ps-platform-backend.service
Wants=network-online.target
Requires=docker.service

[Service]
Type=simple
User=ec2-user
SupplementaryGroups=docker
WorkingDirectory=/home/ec2-user/ps-platform/judge-worker
EnvironmentFile=/etc/ps-platform/judge-worker.env
ExecStartPre=/usr/bin/test -x /home/ec2-user/ps-platform/judge-worker/judge-worker
ExecStart=/home/ec2-user/ps-platform/judge-worker/judge-worker
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`systemd`에 데몬 등록

```bash
sudo systemctl daemon-reload
sudo systemctl enable ps-platform-judge-worker
sudo systemctl list-unit-files | grep ps-platform
```

## 8. 리버스 프록시 설정

현재는 문제가 있다. 현재 흐름은 아래와 같다.

1. 브라우저에서 EC2에 접속하면 기본적으로 80번 포트의 Nginx로 요청이 들어간다.
2. `POST /api/users` 요청은 `http://1.2.3.4/api/users`로 전송된다.
3. 80번 포트로 들어왔으므로 요청을 받는 것은 Spring Boot가 아니라 Nginx이다.
4. Nginx에는 `/api/users`라는 정적 파일이 없으므로 404 에러를 반환한다.

따라서 `/api/`로 시작하는 요청을 8080번 포트에서 실행 중인 Spring Boot로 전달하도록 리버스 프록시를 설정해야 한다.

```bash
sudo nano /etc/nginx/default.d/api.conf
```
아래 내용을 작성한다.

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```
설정 적용

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 9. Nginx SPA 라우팅 설정

아직 문제가 남아 있다. 현재 흐름은 아래와 같다.

1. 브라우저 주소창에 `/problems/1`을 직접 입력한다.
2. Nginx는 `/usr/share/nginx/html/problems/1` 경로에서 파일을 찾는다.
3. 파일이 존재하지 않으므로 `404 Not Found`를 반환한다.

반면 웹사이트 내부에서 버튼을 눌러 이동하면 Nginx가 아닌 React가 URL에 맞는 화면을 렌더링하므로 정상적으로 동작한다.

따라서 `SPA(Single Page Application)` 라우팅을 설정해야 한다.

```bash
sudo nano /etc/nginx/default.d/spa.conf
```

아래 내용을 추가한다.

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

설정을 반영한다.

```bash
sudo nginx -t
sudo systemctl reload nginx
```

`try_files $uri $uri/ /index.html;`의 동작 방식은 아래와 같다.

1. 요청 URI와 동일한 파일을 찾는다.
2. 동일한 디렉터리를 찾는다.
3. 둘 다 없으면 `index.html`을 반환한다.
4. React가 URL을 확인하고 적절한 페이지를 렌더링한다.
