# CSRF (Cross-Site Request Forgery)

> 사용자가 인증된 상태를 악용해 사용자의 의도와 무관한 요청을 서버에 보내도록 만드는 공격

## 공격 과정

은행 송금을 예로 들면 다음과 같다.

```text
악성 링크 클릭
    ↓
은행 서버에 송금 요청
    ↓
로그인 쿠키 자동 포함
    ↓
공격자 계좌로 송금
```

공격자는 다음과 같은 요청을 보내는 링크를 만들 수 있다.

```text
https://bank.com/transfer?to=attacker&amount=100000
```

사용자가 은행에 로그인한 상태에서 공격자가 만든 링크를 클릭하면 브라우저는 로그인 쿠키를 자동으로 포함해 요청을 보낸다. 서버가 CSRF 검증을 하지 않으면 사용자의 의사와 관계없이 공격자 계좌로 송금될 수 있다.

이러한 방식으로 다음과 같은 동작을 실행하게 만들 수 있다.

- 공격자 계좌로 송금
- 비밀번호 또는 이메일 변경
- 관리자 계정으로 공격자의 권한 변경

공격자는 사용자의 로그인 정보를 직접 탈취하지 않아도 인증된 사용자의 권한으로 요청을 보낼 수 있다. 서버에는 정상적인 로그인 쿠키가 전달되므로 사용자가 의도한 요청인지 구분하기 어렵다.

공격자는 자신의 계정으로 기능을 실행 후 응답/요청 구조를 분석해 필요한 요청 형식을 파악할 수 있다.

## 예방 방법

CSRF 방어의 핵심은 해당 요청이 사용자가 의도한 요청인지 확인하는 것이다.

### 1. HTTP 메서드 구분

송금, 비밀번호 변경, 회원 탈퇴처럼 상태를 변경하는 작업은 `GET`으로 처리하지 않고 `POST`, `PUT`, `PATCH`, `DELETE` 등을 사용해야 한다.

하지만 HTTP 메서드를 구분하는 것만으로 CSRF를 방지할 수는 없다. 공격자도 외부 사이트의 폼을 이용해 `POST` 요청을 보낼 수 있으므로 별도의 방어 수단이 필요하다.

### 2. CSRF 토큰 사용

CSRF 토큰은 정상적인 페이지에서 발급받은 요청인지 확인하기 위한 예측하기 어려운 문자열이다.

1. 사용자가 송금 페이지에 접속하면 서버는 CSRF 토큰을 생성한다.
2. 사용자가 송금 버튼을 누르면 다음 정보가 서버로 전달된다.

    ```text
    세션 쿠키: sessionId=abc123
    CSRF 토큰: a8f3d91c...
    송금 계좌: attacker
    송금 금액: 100000
    ```

3. 서버는 저장해 둔 토큰과 요청에 포함된 토큰을 비교한다.

    ```text
    서버가 발급한 토큰 = 요청으로 전달된 토큰
    → 요청 허용

    서버가 발급한 토큰 ≠ 요청으로 전달된 토큰
    → 요청 거부
    ```

공격자의 사이트에서는 유효한 CSRF 토큰 값을 알기 어려우므로 정상적인 요청을 위조하기 어렵다.

### 3. SameSite 쿠키 사용

`SameSite`는 다른 사이트에서 시작된 요청에 쿠키를 함께 보낼지 결정하는 쿠키 속성이다.

```text
정상 사이트: https://bank.com
공격 사이트: https://evil.com
```

`evil.com`에서 `bank.com`으로 요청을 보내는 경우, `SameSite` 속성은 해당 요청에 `bank.com`의 쿠키를 포함할지 제어한다.

> `SameSite`에서 같은 사이트는 스킴과 등록 가능한 도메인이 같은 경우를 의미한다.
>
> ```text
> https://www.example.com
> https://api.example.com
> ```
>
> 두 주소는 같은 사이트이다. `http://example.com`과 `https://example.com`은 스킴이 다르므로 다른 사이트이다.

쿠키는 다음과 같이 설정한다.

```http
Set-Cookie: sessionId=abc123; SameSite=<값>
```

`SameSite`는 `Strict`, `Lax`, `None`으로 설정할 수 있다.

1. `Strict`: 다른 사이트에서 시작된 요청에는 쿠키를 보내지 않는다. (엄격)
2. `Lax`: 다른 사이트에서 이동하는 최상위 탐색이면서 안전한 HTTP 메서드를 사용하는 경우에는 쿠키를 보낸다. (덜 엄격)

    ```text
    외부 사이트의 링크 클릭 → bank.com으로 GET 이동
    → Lax 쿠키 전송 O

    외부 사이트의 이미지 요청 또는 POST 폼 전송
    → Lax 쿠키 전송 X
    ```

3. `None`: 다른 사이트에서 시작된 요청에도 쿠키를 보낸다. (방어 안함)

`SameSite`는 CSRF 위험을 낮추는 방어 수단이며, 필요한 경우 CSRF 토큰과 함께 사용한다.
