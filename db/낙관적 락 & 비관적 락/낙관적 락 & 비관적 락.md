# 낙관적 락 & 비관적 락

```text
1. A가 R1을 읽는다.
2. B가 R1을 읽는다.
3. A가 R1을 수정한다.
4. B가 R1을 수정한다.
```
세션 A가 커밋을 수행하지 않은 상태에서 세션 B가 동시에 같은 데이터를 수정하면 동시성 문제가 발생할 수 있다.
이를 방지하려면, 한 세션이 데이터를 수정하는 동안(커밋 또는 롤백 전까지) 다른 세션이 해당 데이터를 수정하지 못하도록 막아야 한다.
이것이 락(Lock)이다.

## 락의 동작 방식
락은 트랜잭션 단위로 동작한다.

1. 트랜잭션 시작
2. 데이터에 접근할 때 락 획득
3. 데이터 읽기 / 수정
4. 커밋 또는 롤백
5. 락 해제 → 다른 세션이 해당 데이터에 접근 가능

락을 보유하고 있는 시간이 길수록, 다른 세션의 대기 시간도 늘어난다.
따라서 트랜잭션은 짧게 유지하는 것이 중요하다.

## 낙관적 락 (Optimistic Lock)
> 어차피 충돌 잘 안 나겠지. 근데 마지막에 확인은 해볼게.

- 충돌이 발생하지 않는다고 가정하고, 데이터를 읽을 때 락을 걸지 않는다. (비선점 락)
- 대신 커밋 시점에 '내가 읽었을 때와 지금 데이터가 같은가?'를 확인한다.

### 동작 방식

테이블에 `version` 컬럼을 추가해 변경 여부를 추적한다.

버전 번호를 체크할 때는 숫자 버전이나 타임스탬프를 사용할 수 있다.

1. 데이터를 읽을 때 `version` 값도 함께 읽어둔다.
2. 수정할 때, DB에 저장된 `version`이 읽었을 때와 같은지 확인한다.
3. **같다면** → 수정 성공, `version`을 1 증가
4. **다르다면** → 누군가 먼저 수정했다는 뜻 → 충돌 처리
    - 레코드의 버전이 다르면, 트랜잭션을 중단하고 다시 시작할 수 있다.

```sql
-- 낙관적 락 예시
-- 1. 데이터 읽기 (락 없음)
SELECT nickname, version FROM members WHERE id = 42;
-- 결과: nickname = 'oldName', version = 5
 
-- 2. UPDATE 시 version 확인
UPDATE members
SET nickname = 'newName', version = 6
-- 내가 읽었을 때의 version과 지금 DB version이 같아야만 업데이트 됨
WHERE id = 42 AND version = 5;
-- 업데이트된 행이 0개라면 → 다른 세션이 먼저 수정한 것 → 충돌 처리
```

동시 접근은 많지만, 같은 데이터를 동시에 수정하는 경우가 드물 때 유리하다.
- 회원 프로필 수정
- 게시글 수정
- 주문 상태 변경

## 비관적 락 (Pessimistic Lock)
> 혹시 모르니, 내가 끝날 때까지 아무도 건드리지 마!

- 충돌이 발생한다고 가정하고 락을 건다. (선점 락)
- 락을 보유한 세션이 끝날 때까지 다른 세션의 수정을 막는다.

### 동작 방식

1. 데이터를 읽을 때 즉시 락 획득 (`SELECT FOR UPDATE`)
2. 다른 세션이 해당 데이터를 수정하거나 `FOR UPDATE`로 읽으려 하면 대기 상태로 전환 (`일반 SELECT`는 가능)
3. 락을 보유한 세션이 커밋 또는 롤백하면 락 해제
4. 대기 중이던 세션이 락을 획득하고 작업 진행

```sql
-- 비관적 락 예시
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 이 시점부터 다른 세션은 id = 1 행을 수정하거나 SELECT FOR UPDATE로 읽을 수 없음
UPDATE accounts SET balance = balance - 50000 WHERE id = 1;
COMMIT;
```

충돌 가능성이 높고, 동시에 수정되면 안 되는 핵심 데이터를 처리할 때 유리하다.
- 은행 계좌 잔액 변경
- 항공권 / 콘서트 티켓 좌석 예매
- 창고 재고 차감
