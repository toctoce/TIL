# TIL Writer

이 레포의 TIL 문서를 작성하거나 다듬을 때 사용한다.

## 기본 규칙

- 문서는 `#` 제목으로 시작한다.
- 주요 섹션은 `##`를 사용한다.
- 내용은 핵심 위주로 짧고 명확하게 작성한다.
- 필요 이상으로 긴 배경 설명은 줄인다.
- 오타, 맞춤법, 띄어쓰기는 자연스럽게 수정한다.

## 문서 구조

- 정의를 작성할 때는 문서 상단에서 `>` 문법을 사용해 짧게 작성한다.
- 문서마다 내용에 맞게 구조를 정한다.
- 비교가 필요한 내용은 표로 정리한다.
- 절차가 필요한 내용은 번호 목록으로 정리한다.
- 사용자가 참고 URL을 제공했거나 URL을 문서에 추가해 달라고 요청한 경우에만 문서 맨 아래에 `## REFERENCE`를 작성한다.
- 별도의 참고 URL이 없다면 `## REFERENCE`를 추가하지 않는다.

## 코드와 용어

- 문법, 명령어, 파일명, 옵션은 백틱으로 감싼다.
- 처음 등장하는 중요한 개발 용어는 필요할 때만 백틱으로 감싼다.
- 백틱을 너무 많이 사용해서 가독성을 해치지 않는다.
- 코드 예시는 fenced code block을 사용한다.
- 이미지 링크 경로는 항상 `<...>`로 감싼다.
- 이미지 등 추가 파일 이름은 `주제 + 숫자` 형식으로 작성하고 문서 링크에도 반영한다.
- README의 학습 기록 이미지는 예외로 `assets/Study Log.svg`를 사용한다.

## README 규칙

- 새 TIL 문서를 만들면 `README.md`의 알맞은 카테고리에 링크를 추가한다.
- README의 파일 경로는 항상 `<...>`로 감싼다.
- TIL 문서를 작성하거나 수정하면 `assets/Study Log.svg`의 해당 날짜를 작성 상태로 변경한다.
- 해당 날짜의 셀이 이미 작성 상태라면 중복으로 추가하거나 기록 일수를 늘리지 않는다.
- 필요한 주차나 월이 SVG에 없다면 기존 디자인을 유지하면서 범위를 확장한다.
- 잔디밭을 수정할 때 SVG의 총 기록 일수도 함께 갱신한다.
- 새벽 5시 전이면 전날 날짜로 적용한다.

## 피드백 규칙

- 사용자가 피드백을 요청하면 고칠 점만 말하고 잘한 점은 말하지 않는다.
- 고칠 점은 번호 리스트로 작성하고, 확실히 틀린 내용은 수정하며 애매한 내용은 사용자 판단이 필요하다고 말한다.
- 기존 문서의 피드백과 수정을 요청받으면 사용자가 작성한 내용의 오타, 오류, 문장, 가독성만 수정한다.
- 사용자가 작성하지 않은 설명, 예시, 단계, 개념을 추가하고 싶다면 파일에는 반영하지 않고 피드백으로만 제안한다.
- 사용자가 새로운 내용을 추가해 달라고 명시적으로 요청한 경우에만 파일에 내용을 추가한다.
