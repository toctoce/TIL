# 로드 밸런싱

> 로드 밸런싱은 여러 서버에 요청을 분산시켜 특정 서버에 트래픽이 몰리지 않도록 하는 방식이다.

## 사용 이유

- 하나의 서버에 요청이 몰리는 것을 방지한다.
- 서버 장애가 발생했을 때 다른 서버로 요청을 보낼 수 있다.
- 서버를 추가해 더 많은 트래픽을 처리할 수 있다.

## 확장 방법

![Scale Up, Scale Out](<로드 밸런싱 1.png>)

### Scale Up

> 서버 자체의 성능을 높이는 방식이다.

장점

- 추가적인 네트워크 연결이 필요하지 않아 인프라 구조를 단순하게 유지할 수 있다.
- 서버가 한 대라서 데이터 일관성을 유지하기 쉽다.

단점

- 서버 한 대에 문제가 생기면 서비스 장애로 이어질 수 있다.
- 성능을 높일수록 비용이 크게 증가하고, 업그레이드할 수 있는 범위에 제한이 있다.

### Scale Out

> 서버의 개수를 늘리는 방식이다.

장점

- 서버를 유연하게 확장할 수 있고, 확장에 제한이 비교적 적다.
- 서버 한 대가 다운되어도 다른 서버가 요청을 처리할 수 있다.

단점

- 여러 서버가 함께 동작하는 분산 환경에 대한 이해가 필요하다.(구조가 복잡해짐)
- 데이터 일관성 문제가 발생할 수 있다.
- 요청을 분산하기 위해 로드 밸런서가 필요하다.

## 종류

| 구분 | `L4 Load Balancing` | `L7 Load Balancing` |
| --- | --- | --- |
| 네트워크 계층 | 전송 계층 | 애플리케이션 계층 |
| 로드 밸런싱 기준 | `IP`, `Port` | `URL`, `Header`, `Cookie` |
| 장점 | 빠르다. | 기능이 다양하고 유연하다. |

### L4 Load Balancing

- `IP`, `Port` 번호를 기준으로 로드 밸런싱한다.
- 한 대의 서버에서 포트 번호를 다르게 사용해 여러 애플리케이션을 운영한다면 `L4 로드 밸런서`가 필요하다.
- 데이터 내용을 보지 않고 패킷 레벨에서만 분산하기 때문에 속도가 빠르다.
- 다만 데이터 내용을 보지 않기 때문에 섬세한 라우팅은 어렵다.
- 사용자 `IP`가 자주 바뀌면 연속적인 서비스 제공이 어려울 수 있다.

### L7 Load Balancing

- `URL`, `Header`, `Cookie` 등을 기준으로 로드 밸런싱한다.
- `URL`, `Header`, `Cookie` 값에 따라 요청을 세분화해서 서버로 전달할 수 있다.
- 결제, 회원가입처럼 기능별로 다른 서버에서 처리하도록 분산할 수 있다.
- 보안 기능이 결합된 경우 악의적이거나 비정상적인 요청을 감지할 수 있다.
- 데이터 내용을 확인해야 하므로 자원 소모가 크다.

## 로드 밸런싱 알고리즘

### Round Robin

- 서버에 순서대로 요청을 분배한다.
- 로드 밸런싱에서 가장 많이 사용되는 방식이다.
- 요청을 빠르게 서버로 분산할 수 있다.
- 모든 서버의 스펙이 동일한 경우에 사용하기 좋다.

### Weighted Round Robin

- 서버마다 처리량을 가중치로 설정하고, 가중치가 높은 서버에 더 많은 요청을 전달하는 방식이다.
- 예: A 서버 가중치 3, B 서버 가중치 1 → 8개의 요청을 A 서버에 6개, B 서버에 2개 분배

### Least Connection

- 요청이 들어온 시점에 연결 수가 가장 적은 서버로 요청을 보낸다.
- 트래픽이 일정하게 분배되지 않을 때 사용하기 좋다.

### Least Response Time

- 서버 연결 상태와 응답 시간을 모두 고려한다.
- 가장 짧은 응답 시간을 가지는 서버에 요청을 보낸다.

### IP Hash

- 클라이언트 IP를 기준으로 서버를 선택한다.
- IP가 바뀌지 않는다면 계속 동일한 서버로 요청이 전달된다.
